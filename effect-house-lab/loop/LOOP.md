# Effect 루프 규칙서

이 문서는 3시간마다 Windows 작업 스케줄러가 실행하는 무인 회차(`run-tick.ps1` → `claude -p`)의 지침이다. 너는 이전 회차의 기억이 없다. 상태는 모두 아래 파일에 있다. 이 문서를 끝까지 읽고 그대로 한 회차를 실행하라.

## 0. 목적과 사용자 결정 (2026-10-03)
- 목적은 TikTok Effect House 효과를 만들어 게시하고, 반응을 측정하고, 그 결과로 다음 행동을 스스로 정하는 것이다. 사용자는 직접 판단하지 않는다. 판단은 이 루프가 한다.
- 3시간마다 점검·개선한다. 새 효과 제출은 3시간마다 하지 않는다(5장).
- 완성된 효과는 사용자 확인 없이 자동 제출한다. 제출하면 즉시 알린다.
- **첫 효과는 품질이 전부다.** 사용자는 "처음에 퀄 잡는 게 어렵다"고 했다. 첫 제출에는 6장의 첫 출시 게이트를 적용하고, 일정보다 품질을 우선한다.
- **양보다 품질, 그리고 지속적 개선이 원칙이다(사용자가 반복해서 강조했다).**
  - 효과 개수를 늘리는 것은 목표가 아니다.
  - 나온 효과를 데이터로 계속 다듬는 쪽을 새 효과보다 먼저 고른다.
  - 단계를 끝냈다고 완료가 아니다. 그 단계의 결과물이 좋은지 스스로 비판하고, 부족하면 다시 한다.

## 2. 환경과 도구
- 작업 폴더는 `C:\Users\이현상\Workplace\Tiktok`이다. 시작할 때 `git pull`을 한다.
- Effect House는 `C:\Users\Public\EHTest\Launch-EffectHouse.cmd`로만 실행한다. 한글 경로에서는 0xC0000409로 꺼진다.
- **프로젝트는 반드시 영문 경로 `C:\Users\Public\EHTest\Projects\<effect-id>\`에 저장한다.**
- 화면 조작은 `loop/tools/scr.ps1`로 한다.
  - shot, click, dclick, keys, idle, focus를 지원한다.
  - 좌표는 VirtualScreen 기준이고, 모니터가 2대라 원점이 음수일 수 있다. 캡처 결과에 나오는 origin을 더해서 계산한다.
  - 클릭 전에 `focus -Text "Effect House"`를 실행한다.
  - 클릭 후에는 반드시 다시 캡처해서 결과를 확인한다. 눈으로 확인하지 않은 클릭 결과를 사실로 기록하지 않는다.
- PowerShell 5.1은 BOM 없는 UTF-8 `.ps1`의 한글을 깨뜨린다. 새 `.ps1`은 UTF-8 BOM으로 저장한다.
- 스크린샷은 크게 찍고 필요한 영역만 잘라서 본다. 토큰을 아낀다.

## 3. 회차 순서

### 3-1. 사전 점검 (5분)
1. `git pull`을 한다.
2. 이 문서, `WORKING.md`, `LOOP-LOG.md`의 마지막 3회차, `LEARNINGS.md`, `UI-NOTES.md`를 읽는다.
3. `scr.ps1 -Action idle`로 사람이 PC를 쓰는지 확인한다.
   - 300초 미만이면 사람이 쓰는 중이다. **GUI를 건드리지 않는다.** GUI 없이 할 수 있는 일(분석, 에셋·스크립트 준비, 문서)만 하고 기록한다.
4. Effect House 프로세스를 확인한다.
   - 없으면 실행하고 60초 기다린다.
   - 로그인이 풀렸으면 GUI 작업을 중단하고 사용자에게 알린다(7장).

### 3-2. 관측 (15분 이내)
1. 제출한 효과가 있으면 Projects 또는 효과 관리 화면에서 심사 상태를 읽는다.
   - 상태: 심사 중 / 승인 / 반려
   - 반려면 반려 사유 원문을 기록한다.
2. 승인된 효과는 Analytics에서 수치를 읽는다.
   - Analytics에 있는 지표를 화면에 보이는 이름 그대로 전부 기록한다.
   - 처음 보는 지표 구성이면 `UI-NOTES.md`에 정리해 둔다.
3. 공개된 효과 페이지에 사용 영상이 있으면 표지를 최대 6개 본다.
   - 무엇을 찍었는지, 반응 장면이 있는지, 캡션의 언어와 내용을 본다.
4. `tracker.json`의 해당 효과 `observations`에 추가한다.
   - 형식: `{"at": ISO시각, "review_status", "metrics": {지표명: 값}, "video_notes", "source"}`
   - **읽지 못한 값은 null로 둔다. 추정값을 쓰지 않는다.**

### 3-3. 판단
효과별로 현재 단계(4장)를 정한다. 아래 순서에서 처음 해당하는 행동 **하나**를 고른다.
0. 오늘 회고를 아직 하지 않았고 지금이 09시 이후다 → 3-6 회고를 먼저 한다(최대 20분). 회고를 마친 뒤 아래 1~6 중 하나를 고른다.
1. 반려된 효과가 있다 → 반려 사유를 고쳐 재제출한다. 사유가 기획 자체(정책 위반 등)면 수위 조정판을 만든다.
2. 제작 중인 효과가 있다(`WORKING.md`) → 이어서 만든다.
3. 실험 판정 시점이 됐다(5장) → 판정하고 `LEARNINGS.md`를 갱신한다. 다음 실험을 정하거나 은퇴시킨다.
4. 공개 중인 효과에 아직 해 보지 않은 유망한 개선이 있고, 심사 중인 업데이트가 없다 → 개선 업데이트를 만든다(5장 실험 규칙).
5. 공개 중인 효과의 개선 여지가 바닥났거나 은퇴했다. 그리고 제출 조건(5장)을 만족한다 → 다음 후보를 고르고 `WORKING.md`를 새로 작성해 제작을 시작한다. 직전 효과의 `LEARNINGS.md` 교훈을 기획에 반영한다.
6. 할 일이 없다 → 기록만 하고 끝낸다. 억지로 일을 만들지 않는다.

### 3-4. 실행 (최대 약 110분)
- 큰 단계 하나를 끝낼 때마다 `WORKING.md`를 갱신하고 Effect House 프로젝트를 저장(Ctrl+S)한다. 회차가 중간에 끊겨도 다음 회차가 이어갈 수 있어야 한다.
- 단계를 끝내기 전에 결과물을 캡처해서 스스로 비판한다. "상위 효과 옆에 놓아도 부끄럽지 않은가?"를 묻는다. 아니면 그 단계를 끝내지 말고 고친다. 비판 내용은 `WORKING.md`에 한두 줄 남긴다.
- 같은 문제에 30분 넘게 막히면 우회로를 하나 시도한다. 그래도 막히면 `WORKING.md`에 막힌 지점과 시도한 것을 적고 다른 단계로 넘어간다.

### 3-5. 마무리 (10분)
1. `LOOP-LOG.md`에 회차 기록을 추가한다. 형식은 9장을 따른다.
2. `tracker.json`, `WORKING.md`, 필요하면 `UI-NOTES.md`와 `LEARNINGS.md`를 갱신한다.
3. `git add -A`, `git commit -m "loop: <한 줄 요약>"`, `git push`를 한다. push가 실패하면 기록만 남긴다.
4. PushNotification으로 한국어 2~3줄을 보낸다(7장).

### 3-6. 하루 회고 (하루 1회, 루프 자체의 개선)
최근 8회차의 `LOOP-LOG.md`와 `tracker.json`을 보고 아래를 답한다.
1. **진척:** 회차마다 실제로 앞으로 나아갔나? 같은 단계에서 맴돈 회차가 몇 번인가?
2. **품질:** 결과물의 품질이 올라가고 있나? 게이트 점수 추이를 본다.
3. **반복된 막힘이나 낭비:** 매번 다시 찾는 메뉴, 매번 실패하는 클릭, 쓸데없이 큰 스크린샷 같은 것이 있었나?
4. **데이터:** 공개 효과의 수치 추이와 진행 중인 실험이 가설대로 가고 있나?

답을 `LOOP-LOG.md`에 "## 날짜 · 회고"로 남긴다. 개선할 점은 8장 규칙에 따라 `LOOP.md`, `UI-NOTES.md`, 도구 스크립트에 반영한다. 회고 때 반영한 변경은 다음 회고에서 효과가 있었는지 확인한다.

## 4. 효과 단계
`idea → building → qa → submitted → approved | rejected → live → retired`

### building 하위 단계 (깜빡하면 온다 기준)
| 단계 | 할 일 | 완료 조건 |
|---|---|---|
| B1 | 프로젝트 생성, 영문 경로 저장 | 저장된 `.ehproj` 경로를 기록 |
| B2 | 기술 검증 | 기획서 6장 "확인 필요" 3가지의 결과가 각각 성공 / 실패+대안으로 기록됨 |
| B3 | 회색 시제품 | 내장 미리보기 영상에서 시작 → 7번 깜빡임 → 덮침 → 결과까지 한 번 끝까지 돎 |
| B4 | 튜닝 | 내장 미리보기 영상 3종 이상에서 깜빡임 오인식이 한 판당 1회 미만이고, 진행 시간이 15~35초 |
| B5 | 아트·사운드 | 직접 만든 원본 형체와 효과음. 저작권 있는 소재는 쓰지 않음 |
| B6 | 결과 4컷, 아이콘, 데모 영상 | 6장 게이트 통과 |
| B7 | 제출 | 제출 화면 캡처, `tracker.json` 갱신, 알림 |

아트는 Effect House 내장 에셋 라이브러리와 생성 도구, 직접 그린 SVG/PNG를 쓴다. 유료 에셋은 쓰지 않는다.

## 5. 제출·실험 규칙
- 새 효과 제출은 **24시간에 최대 1개**다. 직전에 제출한 효과의 심사 결과가 나온 뒤에만 낸다.
- 수정 업데이트도 다시 심사를 받는다. 업데이트 한 번에 **바꾸는 것은 한 가지**만 해서 효과를 귀속할 수 있게 한다.
- 실험은 `tracker.json` 효과의 `experiments`에 기록한다.
  - 형식: `{"id", "started_at", "change", "hypothesis", "metric", "judge_after", "result"}`
  - 승인 후 최소 48시간이 지나야 판정한다.
- 승인 후 판정 시점은 D1, D3, D7, D14다.
  - 초기 기준(가설이며 데이터로 보정한다): D3 사용 영상 수 20개 미만이면 약함, 20~500개면 보통, 500개 초과면 강함
  - **강함:** 핵심 메커닉은 건드리지 않는다. 대신 마감 품질, 아이콘·데모 영상, 결과 화면을 다듬는 실험을 계속한다. 학습은 `LEARNINGS.md`에 정리한다. 실험 2개가 연달아 효과가 없으면 개선 여지가 바닥난 것으로 보고 다음 효과로 간다.
  - **보통:** 병목 하나를 골라 실험한다. 병목 후보는 다음과 같다.
    - 노출 대비 사용: 아이콘, 데모 영상, 이름
    - 사용 대비 게시: 결과 화면, 반응 장면
    - 진행 시간
  - **약함:** 실험 2개가 실패하면 그대로 공개해 두고 은퇴 처리한다. 다음 후보로 넘어간다.
- 기준값은 실제 데이터가 3개 이상 쌓이면 `LEARNINGS.md`에 근거를 남기고 이 장에서 보정할 수 있다(8장).

## 6. 품질 게이트

### 공통 (모든 제출)
- [ ] Effect House 미리보기에서 시작부터 결과, 다시하기까지 끊김 없이 돈다.
- [ ] 얼굴 영역을 가리는 UI가 없고, 카메라 화면을 덮는 시간이 1초 미만이다.
- [ ] 글 없이 3초 안에 무엇을 할지 안다. 문구는 영어 1~3단어까지만 쓴다.
- [ ] 유명 캐릭터, 로고, 상용 음원을 쓰지 않는다. 피와 고어가 없다. 점프 스케어 강도는 순한 쪽으로 설정한다.
- [ ] Effect House 성능, 용량 경고가 없다.
- [ ] 이름, 설명, 해시태그는 영어로 쓴다. 이름은 짧고 규칙이 보여야 한다.

### 업데이트 회귀 검사 (공개 효과 수정 시)
- [ ] 바꾼 한 가지 말고는 기존 흐름이 그대로 돈다(시작 → 결과 → 다시하기).
- [ ] 첫 출시 게이트의 채점 항목 중 어느 것도 이전 점수보다 내려가지 않는다.

### 첫 출시 게이트 (첫 효과에 추가)
- [ ] 내장 미리보기 영상 3종 이상(조명과 얼굴이 다른 것)에서 각각 끝까지 돌리고 단계별 캡처를 남긴다.
- [ ] 상위 효과 대표 화면 3개와 내 효과의 시작 화면, 덮치는 순간, 결과 화면을 나란히 놓고 비교한다. 아래 항목을 1~5점으로 엄격하게 채점하고, **모두 4점 이상**이어야 한다. 점수와 이유는 `LOOP-LOG.md`에 남긴다.
  - 첫 화면 흡인력
  - 아트 완성도
  - 덮치는 순간의 임팩트
  - 결과 화면의 공유 욕구
  - 마감 품질(정렬, 전환, 소리)
- [ ] 3점 이하 항목이 있으면 고치고 다시 채점한다. 이 게이트는 일정 때문에 낮추지 않는다.
- [ ] 아이콘과 데모 영상을 각각 2안 이상 만들어 비교한 뒤 고른다.

## 7. 알림 (PushNotification)
- **매 회차:** 회차 끝에 2~3줄로 보낸다. 예: "깜빡하면 온다 B3 진행 중: 깜빡임 인식 확인 완료, 형체 레이어 작업 중. 다음 회차는 미리보기 전체 흐름."
- **즉시 알림:** 제출, 승인, 반려가 생기면 바로 보낸다.
- **사용자 조치 필요:** 로그인 만료, 같은 문제로 3회차 연속 막힘, 비용·계정 결정이 필요할 때 보낸다. 무엇을 해야 하는지 한 문장으로 쓴다.
- 쉬운 한국어로 쓴다. 내부 용어(B3, observations 등)는 풀어서 쓴다.

## 8. 루프 자체의 개선
- **바로 고쳐도 되는 것:** `UI-NOTES.md`, `WORKING.md`, 이 문서의 절차상 오류(경로, 메뉴 위치, 도구 사용법)
- **근거가 있어야 고치는 것:** 5장의 기준값, 3-3의 우선순위. `LEARNINGS.md`에 근거를 남기고, `LOOP-LOG.md`에 "규칙 변경: 무엇을, 왜"를 적은 뒤 바꾼다.
- **고치지 않는 것:** 0장의 사용자 결정, 10장의 금지 사항, 5장의 제출 빈도 상한

